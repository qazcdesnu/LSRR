# `lsrr/analysis/` — 메커니즘 분석

## 역할
제안서 §7의 메커니즘 분석. **왜 되는가(혹은 왜 안 되는가)**를 저장된 트레이스로부터 사후 규명한다.

## 경계
- **한다:** 저장된 트레이스와 체크포인트를 읽어 분석 산출물을 만든다.
- **하지 않는다:** 학습하지 않는다. 트레이스를 새로 만들지 않는다(필요하면 평가를 다시 돌린다). **분석이 학습 경로에 개입해서는 안 된다.**

## 모듈

| 모듈 | 역할 | 대응 §7 항목 | 상태 |
|---|---|---|---|
| `plugin.py` | 플러그인 프로토콜과 트레이스 러너 | — | 계획 |
| `collapse.py` | 표현 동질화·자명해 진단 (랭크, 층간 분산, 쌍별 유사도) | **게이트 ①** | 검증 |
| `hop_convergence.py` | ProsQA 홉 수별 평균 수렴 사이클 | (i) **단조 증가 예측** | 계획 |
| `alpha_profile.py` | 풀링 가중 α_l의 레이어별 분포 | (ii) **중간층 집중 예측** | 계획 |
| `logit_lens.py` | 사이클별 `R⁽ᵐ⁾`를 백본 헤드로 투영, 정제 궤적 시각화 | (iii) | 계획 |
| `backpatch_recovery.py` | back-patching 오라클 상한 대비 회수율 | (iv) | 계획 |

## 핵심 계약

```
BaseAnalysisPlugin.analyze(traces, run_dir) -> dict
```

## 각 분석이 판정하는 가설

### `hop_convergence.py` — "홉이 많을수록 오래 생각한다"
수렴 사이클이 홉 수에 따라 단조 증가하지 **않으면**, 수렴 종료가 문제 난이도에 적응하고 있다는 주장의 핵심 근거가 사라진다. 종료 규칙이 난이도가 아니라 다른 무엇(예: 답 길이, 표면 형태)에 반응하고 있을 가능성을 따져야 한다.

### `alpha_profile.py` — "중간층 집중"
§3 ①의 논증(유용 정보는 층에 분산되어 있고, 마지막 구간은 정보 삭제·선명화를 담당한다)이 맞다면 α는 중간층에 집중해야 한다. 만약 α가 마지막 층에 몰린다면, 레이어 축 전개를 쓴다는 본 연구의 전제 자체가 이 백본·과제에서 작동하지 않는다는 신호다 — Ablation A의 결과와 교차 확인한다.

### `backpatch_recovery.py` — headroom의 몇 %를 회수했는가
back-patching 연구는 2홉 질의 오답 사례의 32~66%에서 후기 층 상태를 초기 층에 되돌리는 개입만으로 정답 생성이 가능함을 보였다(**오라클 상한**). 이 수치는 상한이지 베이스라인이 아니며, 인용 시 반드시 그렇게 표기한다 (§9 한계 명시). 학습된 양방향 통로가 그 headroom의 몇 %를 **자동으로** 회수하는가가 §4.2 양방향 논거의 직접 검증이다.
`backbone/interventions.py`의 개입 훅이 오라클 측정을 담당한다.

### `collapse.py` — 자명해로 붕괴하지 않았는가
잠재 반복이 감독 없이 표현 동질화로 붕괴한다는 진단이 있으므로, "성능이 나온다"만으로는 부족하다. 랭크·분산·쌍별 유사도로 상태가 실제로 정보를 담고 있는지 확인한다. 게이트 ①의 판정 데이터다.
